The browser sessions do the work: pages, clicks, errors and application state. Jev answers small questions about that state: did the flow recover, did the release behave correctly, should this result be escalated?

The surrounding program runs those checks in parallel, collects the decisions and reports failures. Jev is one component in the test system.

## 02 — How Jev works

[System One](https://typesafe.ai/blog/introducing-system-one-models-and-jev) is TypeSafe's name for models built to run inside software. Jev is its first public model.

Imagine a support ticket:

```text
state:    "I changed plans and my invoice doubled."
question: route_to
answers:  billing | technical | sales
```

An ordinary language model usually returns a string. Your application then parses the answer, validates it, retries it, and hopes the answer does not change the workflow.

Jev returns a value from the allowed set and a probability for the decision. In this example, the result might be `billing` with high confidence. The code can route the ticket, ask for review, or call another tool.

The useful abstraction is simple:

> Give the model state and a fixed question. Get back a decision that code can use.

Matija Šošić puts it plainly in [his short explanation](https://x.com/MatijaSosic/status/2100190746389135772): Jev is classifier-like, accepts unstructured text, and does not require a separate training run for every use case.

## 03 — Why this is different from JSON mode

JSON mode changes the shape of an LLM's answer. The model still generates text one token after another and the application still depends on that generation behaving correctly.

Jev starts with a different contract. The possible output shape is defined in advance. The model is trained and served to answer typed questions, and TypeSafe says it samples those decisions in parallel.

With an LLM, the program interprets a response. With Jev, the program receives the decision it needs.

The distinction:

| Traditional LLM | System One / Jev |
| --- | --- |
| Generates a string | Returns a typed decision |
| Samples token by token | Samples decisions in parallel |
| Needs parsing before code can act | Fits directly into workflow control |

## 04 — The model becomes a fuzzy if-statement

Software is full of decisions that are too messy for a hard-coded rule and too frequent to justify a long chat-model call.

Route a request, score a risk, decide whether to retry, inspect browser state, and escalate only when confidence is low.

Each one belongs inside a larger program as a decision, not a paragraph.

TypeSafe calls Jev's training approach RLCD, or Reinforcement Learning for Calibrated Decisions. Jev picks an answer and returns a probability, so the workflow can choose between automatic action and human review.

That is the part I care about: AI can be a probabilistic function inside an otherwise ordinary system.

## 05 — Jev gives up open-ended text

Use a general model for conversation, explanation, or code. Use Jev when the application already knows the question and the actions that can follow.

TypeSafe reports 70 to 500 millisecond response times, $0.042 per million input tokens, and speed and cost gains of 20 to 200 times and 40 to 400 times on its System One tasks. These are early, self-reported numbers. The trade-off is less freedom in exchange for a cheaper, faster and more predictable decision primitive.

Type safety also does not make a decision true. It guarantees the shape, not the meaning. The surrounding code still needs to set thresholds, handle uncertainty and decide what happens when the model is wrong.

[TypeSafe raised a $40 million seed round led by DCVC](https://www.dcvc.com/news-insights/typesafe-emerges-from-stealth-with-a-new-way-of-doing-ai/). The money is a bet that software will need many small decisions more often than it needs another paragraph.

The most useful AI model may be the one that writes nothing.

## Coda

Software can use both kinds of model: one for explanations and open-ended work, another for the thousands of decisions around it.
